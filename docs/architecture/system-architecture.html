01 · Executive summary

A visual automation platform built around durable runs

Nodebase lets users compose a workflow on a drag-and-drop canvas, connect trigger and action nodes, and run it reliably. The product combines a Next.js monolith for UI and APIs with Inngest for durable execution, Redis-backed queues for scheduling and email, and PostgreSQL as the system of record.

What the system does

  • Build: users create workflows in a React Flow editor. Nodes and connections are persisted through tRPC and Prisma.
  • Trigger: a run starts manually, from a cron schedule, or from an inbound webhook (Google Form, Stripe, Telegram).
  • Execute: a single Inngest function loads the graph, topologically sorts it, and threads a shared WorkflowContext through per-node executors.
  • Integrate: executors call AI providers, HTTP endpoints, Telegram, Discord, Slack, and Google Sheets. Credentials are decrypted only inside the server-side executor.
  • Observe: every run is stored as an Execution; per-node status is published over Inngest Realtime and rendered live on the canvas.
  • Monetise: Better Auth handles identity; Polar gates premium capabilities such as credentials creation and unlimited workflow creation.

Architectural shape

Modular monolith + managed execution

The Next.js application owns pages, tRPC, auth, webhooks, and the Inngest function endpoint. Execution state and retries are delegated to Inngest rather than run in the request cycle. This keeps the UI fast and gives long-running AI/HTTP work durable retries.

Database as source of truth

Workflows, nodes, connections, credentials, and executions live in PostgreSQL. Inngest events carry only a workflow id plus optional initial data; the function re-reads the graph from the database at execution time.

Feature-first code organisation

Each product area owns its tRPC router, prefetch helpers, nuqs params, hooks, and components under src/features. Routers are composed once in src/trpc/routers/_app.ts.

Registry-driven node system

A node type appears in the editor, executes at runtime, and streams status because it is registered in the Prisma enum, realtime channel map, executor registry, React Flow node registry, and node selector.

DurabilityInngest functions with step-based execution, 3 retries in production, failure handler marking executions FAILED, and per-step memoisation.

03 · System context

The system boundary and external actors

Nodebase is a multi-tenant web application. Authenticated users and machines (through webhooks) enter through the Next.js application. Work is executed asynchronously by Inngest using executors that call third-party APIs.

Actors

ActorInteraction
End userSigns up / logs in, creates and edits workflows, configures nodes and credentials, runs workflows, views execution history and node status.
Webhook providerSends Google Form responses, Stripe events, or Telegram updates to public route handlers. These requests are not session-authenticated; they are protected by per-workflow rate limits, idempotency keys, and provider-specific secrets.
InngestReceives events, calls the served function at /api/inngest, retries failed steps, and relays published realtime messages.
Scheduler / workerA separate BullMQ cron worker fires Inngest events at scheduled times. The email worker sends OTP messages outside the request cycle.
Third-party APIsAI providers, Telegram, Discord, Slack, Google Sheets, arbitrary HTTP endpoints, SMTP, GitHub/Google OAuth, and Polar billing.
Boundary rule The Next.js application is the only public entry point. Background workers never expose HTTP. Inngest executes logic inside the deployed Next.js container through /api/inngest, so executors have access to the same Prisma client, encryption key, and environment configuration as the web tier.

npm run dev:all starts mprocs, which supervises five processes: ngrok (public webhook tunnel), Inngest dev server, email worker, cron worker, and the Next.js dev server with Turbopack. npm run inngest:dev starts only the Inngest dev UI; the application serves functions at /api/inngest.

Production build and packaging

Vercel

vercel.json sets the build command to npm run vercel-build, which runs prisma generate && next build. Prisma targets native and rhel-openssl-3.0.x. Sentry wrapping is enabled only when SENTRY_AUTH_TOKEN is present.

Docker / EKS

The Dockerfile uses three stages: deps (npm ci, Prisma generate), builder (Next build with standalone output), and runner (non-root nextjs user, standalone server, Prisma schema and CLI). node:22-slim with OpenSSL is used because Prisma needs it.

Operational note Cron and email workers are not started by the Next.js container. A deployment must run them as separate processes/services, otherwise cron schedules will be registered but never fired and OTP emails will queue without being delivered.

Server page pattern

  1. requireAuth() reads the session from request headers and redirects unauthenticated users to /login. Auth pages use requireUnauth() to redirect signed-in users to /workflows.
  2. A feature-specific prefetch helper calls the tRPC query options proxy and primes a per-request React Query client created with cache(makeQueryClient).
  3. <HydrateClient> dehydrates the query cache into a HydrationBoundary, so client components render instantly without a loading flash.
  4. Client components use useSuspenseQuery through feature hooks and mutate via tRPC, invalidating related query keys on success.

Procedure tiers

ProcedureBehaviour
baseProcedureRaw tRPC procedure with SuperJSON transformer. No session requirement.
protectedProcedureCalls auth.api.getSession({ headers }) and throws UNAUTHORIZED when no session exists. The resolved session is attached to ctx.auth.
premiumProcedureBuilds on protected: fetches the Polar customer by external id and throws FORBIDDEN unless at least one active subscription exists.
Important implementation detail createTRPCContext is a stub that returns { userId: "user_123" }. Authorization must rely on ctx.auth.user.id set by protectedProcedure, never on ctx.userId.

07 · Data model

PostgreSQL schema and relationships

The schema separates identity (Better Auth tables), tenant-owned assets (workflows and credentials), graph structure (nodes and connections), and run history (executions).

Model notes

EntityDesign notes
UserPrimary key is a Better Auth string id. Email is unique. Relations cascade to sessions, accounts, workflows, and credentials.
WorkflowBelongs to a user. Holds a display name, timestamps, and the graph via child nodes/connections. Deleting a workflow cascades to its graph and executions.
NodeBelongs to a workflow. type is a Prisma enum. position and data are JSON, keeping node-specific configuration flexible without schema changes per node. Optional credentialId links an encrypted credential.
ConnectionDirected edge from one node output to another node input. Uniqueness on (fromNodeId, toNodeId, fromOutput, toInput) prevents duplicate edges. Cascades when either node is deleted.
CredentialType is one of ANTHROPIC, GEMINI, OPENAI, TELEGRAM, GOOGLE_SHEETS. value stores the Cryptr-encrypted secret. Never sent decrypted to the browser.
ExecutionOne row per run. inngestEventId is unique and links the row to the Inngest event. Status is RUNNING/SUCCESS/FAILED; error text and stack are stored for failed runs; output holds the final workflow context.
Session, Account, VerificationManaged by Better Auth/Prisma adapter. Account stores OAuth tokens or password hash; Verification supports OTP/verification flows.

Tenancy and integrity

  • Ownership is enforced in query predicates: workflows and credentials are always read or mutated with userId: ctx.auth.user.id; executions are filtered through workflow.userId.
  • Workflow creation locks the user row with SELECT ... FOR UPDATE inside a transaction before counting workflows, preventing concurrent creates from bypassing the free-tier limit.
  • Workflow updates run in a transaction: nodes are upserted, removed nodes are deleted, connections are replaced, and the workflow timestamp is touched.
  • Migrations are checked into prisma/migrations; the Prisma client is generated into src/generated/prisma at install/build time.
08 · Authentication & billing

Identity, OTP delivery, OAuth, and premium gating

Better Auth is the identity provider embedded in the Next.js app. It uses Prisma/PostgreSQL for persistence, email OTP for verification, social OAuth for convenience, and a Polar plugin for subscriptions.

Authentication capabilities

CapabilityImplementation
Email + passwordBetter Auth email/password enabled with auto sign-in. Email verification is required before access; signup and sign-in can resend verification.
Email OTPemailOTP plugin: 6 digits, 5-minute expiry, hashed storage, 5 allowed attempts, overrides default email verification. Sending is delegated to enqueueOtpEmail.
OTP cooldownA custom Better Auth plugin intercepts /email-otp/send-verification-otp before a new code is generated. otpSendAllowed(email) prevents burning the queue and invalidating a previously sent code.
OAuthGitHub and Google social providers configured from environment secrets. Trusted origins include the app URL, auth URL, and localhost variants.
Rate limitsGlobal Better Auth limit of 20 requests per 60s; OTP send limited to 3/min; OTP verify limited to 8 per 5 minutes.
SessionsServer components and tRPC procedures call auth.api.getSession({ headers }). Session cookies are handled by the Better Auth route handler at /api/auth/[...all].

Email delivery path

  1. Better Auth generates the OTP and calls sendVerificationOTP.
  2. enqueueOtpEmail adds an otp job to the BullMQ email queue. If Redis is not configured, it falls back to sending inline.
  3. The email worker calls sendOtpEmail, which uses Nodemailer/SMTP. In development without SMTP it logs the OTP instead of failing.
  4. Jobs retry up to 3 times with exponential backoff; completed jobs are removed and the last 1000 failures are retained.

Billing and entitlement

Polar plugin

Creates a customer on signup, exposes checkout for the Nodebase Pro product, and a customer portal. The app uses the Polar SDK in sandbox mode with an access token.

Entitlement checks

premiumProcedure requires at least one active subscription. Credential creation uses it. Workflow creation checks subscription server-side and caps free users at 3 workflows; the usage endpoint reports count, limit, and premium state.

Failure behaviour isActiveSubscriber() catches Polar errors and returns false, so billing outages degrade to free-tier limits rather than crashing workflow creation. Premium tRPC procedures still perform a direct Polar lookup and will reject when it fails.
09 · Visual editor architecture

React Flow canvas, node registry, and save path

The editor is a client-side React Flow instance hydrated with a workflow loaded through tRPC. Node appearance and behaviour are selected by a type registry; graph persistence is handled by a single tRPC mutation.

Client composition

ConcernImplementation
CanvasReactFlow with pan-on-scroll, selection-on-drag, grid snapping, background, controls, and minimap. Nodes and edges are local state initialised from the suspense query result.
Node renderingnodeComponents maps every NodeType to a React component. Shared bases provide consistent handles, status indicators, and layout.
EditingNode/edge changes are applied through React Flow helpers. Non-selection changes set isDirtyAtom. New connections use addEdge.
Editor instanceeditorAtom stores the React Flow instance so the header can call getNodes() and getEdges() when saving.
Node configurationEach node type has a dialog that writes configuration into node.data. Credentials are selected by type and referenced by id; secret values never leave the server.
Execution controlThe execute button is shown only when a manual trigger exists. It calls workflows.execute.
Realtime statusEach node uses useNodeStatus with its channel and a server action that returns an Inngest subscription token. Status values are initial, loading, success, and error.

Save transaction

Pressing Save sends the complete node and edge snapshot to workflows.update. The server verifies ownership, then inside a transaction:

  • Upserts every submitted node by id, updating position and type.
  • Overwrites data only when the client sends a non-empty object, protecting configuration when the editor has an incomplete snapshot.
  • Deletes nodes that no longer exist in the submitted graph.
  • Replaces all connections with the submitted edges.
  • Updates the workflow timestamp.
  • After the mutation, the client calls syncCronSchedules to reconcile BullMQ repeatable jobs.
Design choice Node upsert + selective data overwrite is safer than delete-all-and-recreate: it preserves node configuration and ids when the client snapshot is partial, while still allowing node and edge removal.

List and detail pages

Workflows, credentials, and executions share an entity-page pattern: server-side auth and prefetch, URL-driven pagination/search through nuqs, suspense queries on the client, and reusable loading/empty/error states. The editor page sits in a separate route group so it can use a full-height canvas layout without the standard dashboard content shell.

10 · Workflow execution engine

One durable function, ordered node executors, shared context

All runs enter Inngest as workflows/execute.workflow. The single executeWorkflow function creates an execution record, loads the graph, sorts it, and runs each node's executor in sequence while publishing live status.

Execution steps

  1. Event validation. The function requires an Inngest event id and workflow id, otherwise it throws NonRetriableError.
  2. Create execution. A step.run("create-execution") inserts an Execution with status RUNNING and the unique Inngest event id. A database conflict is treated as non-retriable.
  3. Prepare workflow. A second step loads nodes and connections and runs topologicalSort. If connections are empty, nodes retain their order. Disconnected nodes are added as self-edges. Cycles raise an error.
  4. Resolve owner. The workflow's userId is loaded and passed to executors so credential lookups remain tenant-scoped.
  5. Initialise context. event.data.initialData seeds the mutable WorkflowContext (for example googleForm, stripe, telegram, or cron).
  6. Execute nodes. For each node, getExecutor(node.type) resolves the implementation. The executor receives node data, id, user id, context, the Inngest step tool, and the realtime publish function.
  7. Thread context. Each executor returns a new context object; results are namespaced by the node's configured variable name so later nodes can reference earlier outputs.
  8. Finalise. A final step sets status SUCCESS, completion time, and the output context. Any unhandled failure triggers onFailure, which marks the execution FAILED and stores the error message and stack.

Executor contract

InputPurpose
dataNode-specific configuration persisted in the JSON column (prompts, endpoint, variable name, credential id, operation, etc.).
nodeIdIdentifies the node for realtime status messages.
userIdScopes credential reads to the workflow owner.
contextAccumulated outputs from earlier nodes; used as the Handlebars template context.
stepInngest step tools, used for memoised/retryable units such as HTTP calls, credential reads, and AI generation.
publishRealtime publish function bound to the node's channel.

Realtime status contract

Every node type has a dedicated Inngest channel. Each published message has the shape { nodeId, status } where status is loading, success, or error. The browser obtains a short-lived subscription token through a server action, then filters the latest message for the node. This is presentation-only state; the durable outcome is the Execution row.

Templating Action nodes compile configuration through Handlebars against the current context. A custom json helper pretty-prints context values, enabling prompts and request bodies to embed prior node output. Validation failures publish error and throw NonRetriableError so Inngest does not retry misconfiguration.
11 · Trigger architecture

Manual, scheduled, and webhook-driven runs

All trigger paths converge on the same Inngest event. They differ in how the event is produced and what initial data is attached.

Trigger comparison

TriggerIngressInitial data and notes
ManualtRPC workflows.executeVerifies workflow ownership, then sends the event with only workflowId. The execute button is visible when a manual trigger node exists.
CronBullMQ repeatable scheduler → cron workerSchedules are stored in cron node data and registered with upsertJobScheduler. Key is cron:<nodeId>:<scheduleId>; timezone, start/end date, and cron pattern are honoured. Worker sends initialData.cron.
Google FormPOST /api/webhooks/google-form?workflowId=Normalises form id/title/response id/timestamp/respondent/responses/raw into initialData.googleForm. Idempotency key uses response id.
StripePOST /api/webhooks/stripe?workflowId=Normalises event id/type/timestamp/livemode/object into initialData.stripe. Idempotency key uses event id.
TelegramPOST /api/telegram/webhook/[workflowId]Resolves the workflow's Telegram trigger node and credential, decrypts the bot token, and validates the Telegram secret header with a timing-safe comparison. Messages become initialData.telegram; callback queries are acknowledged without starting a run.

Schedule reconciliation

Cron schedules are owned by the node data, not by a separate schedule table. When a workflow is saved, syncCronSchedules(workflowId) authenticates the user, filters cron nodes, registers each schedule, and removes schedulers whose node ids no longer exist. Deleting a workflow explicitly removes its cron schedulers before deleting the database row. Upsert semantics make repeated saves idempotent.

Webhook protections

Rate limiting

Upstash sliding-window limiter per workflow: Google Form 30/min, Stripe 120/min, Telegram 60/min by default, configurable through environment variables.

Idempotency

A Redis SET NX EX key with 24-hour TTL suppresses duplicate provider deliveries. When Redis is absent, events are accepted without dedupe.

Origin validation

Telegram uses a derived bot secret and constant-time comparison. Stripe and Google Form rely on provider configuration and workflow-scoped URLs; no session is required.

13 · Security & multi-tenancy

Trust boundaries and data protection

Security relies on session validation inside procedures, ownership predicates on every tenant asset, encryption of secrets, and layered protections for unauthenticated webhooks.

ControlImplementation
AuthenticationBetter Auth sessions validated from request headers. protectedProcedure rejects missing sessions with UNAUTHORIZED. Server pages redirect through requireAuth.
Authorization / tenancyAll workflow, credential, node, and execution access is scoped by the authenticated user or through workflow.userId. There is no cross-tenant id lookup path in the exposed routers.
Plan gatingpremiumProcedure validates active Polar subscriptions. Credential creation is premium-only. Workflow creation enforces a server-side free cap of 3 with a row lock.
Secret storageCredentials are encrypted with Cryptr using ENCRYPTION_KEY. Decryption occurs only inside executors and the Telegram webhook handler, never in list/detail responses.
Webhook authenticityTelegram secret token is derived per bot/workflow and compared with timingSafeEqual. Public webhook URLs are workflow-scoped; rate limits and idempotency reduce abuse and replay.
Abuse preventionBetter Auth global and OTP-specific rate limits; OTP cooldown plugin; Upstash per-workflow webhook limits; duplicate suppression through Redis.
Transport & headersTrusted origins restrict Better Auth callbacks. Production is expected to terminate TLS at the load balancer or platform edge. Dev ngrok origins are explicitly allowed.
Error reportingSentry captures server, edge, and client errors. Execution errors are persisted for user-visible run history.

Trust boundaries

  • Browser → Next.js: session cookie and tRPC/HTTP requests. All inputs validated with Zod at the procedure boundary.
  • Provider → Next.js webhooks: unauthenticated but protected by provider secret/configuration, rate limits, idempotency, and workflow lookup.
  • Next.js → Inngest: signed events via event/signing keys. The function endpoint is served by the app.
  • Executor → third-party API: short-lived server-side call using decrypted credentials; results are returned into the workflow context.
  • App → database/Redis: private network or TLS-managed endpoints, credentials from environment.
Known security gotcha The tRPC context stub must never be used for authorization. Always use ctx.auth.user.id from the session attached by protectedProcedure. The stub userId is a constant and does not represent the caller.
14 · Reliability & observability

Failure handling, retries, and run history

Reliability is achieved through durable execution, explicit non-retriable validation errors, durable run records, and queue-level retry policies.

Failure and retry matrix

ComponentPolicy / behaviour
Inngest functionretries: 3 in production, 0 in development. Steps are memoised; failed steps retry without re-running successful ones.
Node validationMissing endpoint, method, credential, prompt, variable name, spreadsheet id/range, etc. publish error and throw NonRetriableError.
Function failure handleronFailure updates the Execution by unique Inngest event id to FAILED and stores message and stack.
Execution creation conflictUnique inngestEventId protects against duplicate execution rows; the conflict is surfaced as non-retriable.
Email queue3 attempts with exponential backoff (2s), completed jobs removed, up to 1000 failed jobs retained.
Cron queue3 attempts with exponential backoff (5s), completed jobs removed, up to 100 failed jobs retained. Scheduler upserts are idempotent.
Webhook duplicatesRedis SET NX idempotency key returns success without emitting a second event; TTL 24 hours.
Rate limiting outageWhen Upstash REST credentials are absent, rate limiting and idempotency are disabled with warnings rather than breaking ingress.
Billing outageSubscription check for workflow creation degrades to free tier; premium procedures fail closed with FORBIDDEN.

Execution records

Status, timestamps, final output, error message and stack per run. UI exposes history and detail pages.

Realtime events

Per-node loading/success/error messages let users see progress while a durable run is in flight.

Sentry

Server/edge instrumentation plus onRequestError capture. Optional source map upload and tunnel route.

Health endpoint

GET /api/health returns { status: "ok" } for load balancer or platform probes.

Queue admin

Logs

Workers log completed/failed jobs. Email has a development OTP fallback for local testing.

Operational gap The repository does not configure an automated test runner. Verification is expected to be Biome lint, npx tsc --noEmit, and a production build. Adding integration tests around trigger ingress, execution ordering, and tenancy is the highest-value reliability improvement.

Deployment checklist

  1. Provision PostgreSQL and run Prisma migrations. Generate the Prisma client during build.
  2. Provision Upstash Redis. Provide both the REST credentials (rate limit, idempotency) and the ioredis URL (BullMQ).
  3. Configure Inngest cloud with the event and signing keys, and ensure it can reach /api/inngest at the public app URL.
  4. Run the email and cron workers as separate long-lived processes with the same environment and Redis URL.
16 · Design decisions & known risks

Why the system looks like this

The architecture favours a small number of well-understood primitives: one web application, one durable function, explicit registries, and managed state. The trade-offs are intentional.

DecisionRationaleTrade-off
Inngest for workflow executionLong-running AI and HTTP calls need retries, step memoisation, and a failure handler without building a custom job runner.Execution depends on Inngest availability and correct signing/event configuration. The function is served by the web container, so the web tier must remain reachable.
BullMQ for cron and emailRepeatable jobs provide precise cron scheduling with timezones and start/end dates. Email delivery is decoupled from signup latency.Two extra worker processes must be deployed and monitored. Redis is a hard dependency for cron/email.
PostgreSQL as workflow source of truthGraph state is easy to inspect, migrate, and query. Events stay small and point at a workflow id.The graph is re-read at execution time; editing during a run affects only future runs, and very large graphs add query overhead.
Explicit node registriesCompile-time exhaustiveness catches missing executors/renderers. Node behaviour stays colocated and reviewable.Adding a node requires coordinated edits across five areas and a migration.
Encrypt credentials at restProvider secrets are valuable; they should never be readable from the database or client bundle.Key rotation and ENCRYPTION_KEY management become critical operational concerns.
Upsert + selective data overwrite on saveProtects node configuration from incomplete client snapshots while still supporting deletion and rewiring.More complex transaction logic than delete-and-recreate; requires careful client snapshot semantics.
Realtime per-node channelsUsers get immediate visual feedback without polling the database.Status is ephemeral; reconnecting clients may miss transient transitions. Durable history is the Execution row.

Known risks and technical debt

Context stub

createTRPCContext returns a hard-coded user id. Any future code that trusts it for authorization would create a tenant-isolation vulnerability. Keep authentication inside procedures.

OpenAI channel copy-paste bug

The OpenAI executor publishes an Anthropic channel message on the missing-credential branch. This can leave OpenAI nodes visually stuck; the channel import should be corrected.

No automated tests

There is no test runner configured. Regression coverage for topological sort, trigger ingress, idempotency, tenancy, and executor contracts is missing.

Type checking bypassed in build

next.config.ts sets typescript.ignoreBuildErrors: true. CI should run tsc --noEmit explicitly or the build can ship type errors.

Webhook source verification

Stripe and Google Form webhooks are workflow-scoped and rate-limited but do not verify provider signatures in the route handlers. Adding signature verification would harden ingress.

Worker deployment coupling

Cron and email correctness depends on separately running workers. A deployment that only ships the Next.js container silently loses scheduling and email delivery.
